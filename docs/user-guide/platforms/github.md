# GitHub integration guide

GitHub is the primary platform supported by `git-brx`. It handles issue validation, pull request creation, reviewer routing, and post-merge branch cleanup through GitHub's REST API.

---

## 1. Zero-config & auto-detection

If your `origin` remote points to GitHub (e.g., `git@github.com:owner/repo.git` or `https://github.com/owner/repo.git`), `git-brx` works without a configuration file:

- Sets `platform` to `github`.
- Parses `owner` and `repo` directly from `origin`.
- Uses default branch prefixes (`issue/<id>`, `feature/<id>`, `epic/<id>`).
- Routes issue validation and pull request operations to GitHub's REST API.

### Partial configuration
To customize specific settings—like reviewer mappings or branch labels—without repeating the platform boilerplate, define only the fields you want to override in `.git-brx.yaml`:

```yaml
# .git-brx.yaml
review:
  default: [team-lead]
```

`git-brx` still infers `platform: github`, `owner`, and `repo` from `origin` and merges your overrides on top.

## 2. Authentication & Personal Access Token (PAT) setup

`git-brx` calls GitHub's REST API during three commands:
- `git brx create <branch>`: Fetches issue titles, status, and labels.
- `git brx review`: Opens pull requests and requests reviewers.
- `git brx delete`: Checks PR merge status when a remote branch still exists on `origin`.

### Token resolution order
`git-brx` looks for a GitHub token in this order:
1. `GITHUB_TOKEN` environment variable.
2. `GH_TOKEN` environment variable.
3. System Git credential helper (`git credential fill`).

### Creating a Fine-Grained Personal Access Token

#### Step 1: Open Token Settings
1. In GitHub, click your profile icon in the top-right corner and select **Settings**.
2. In the left sidebar under **Access**, click **Credentials** (or **Developer settings** $\to$ **Personal access tokens**).
3. Select **Fine-grained personal access tokens**.
4. Click **Generate new token**.

![GitHub Credentials Navigation](../../../assets/github-token-credentials-nav.png)

#### Step 2: Select Repository Access
Under **Repository access**:
- Choose **Only select repositories** and pick your target repo (e.g., `owner/repo`), or select **All repositories** if you use `git-brx` across all of your repos.

#### Step 3: Set Permissions
Grant only the minimum required repository permissions:

| Permission Category | Scope | Access Level | Why `git-brx` needs it |
| :--- | :--- | :--- | :--- |
| **Repository permissions** | **Issues** | **Read-only** | Reads issue title, status, and labels to validate branch prefixes (`issue/`, `feature/`, `epic/`). |
| **Repository permissions** | **Metadata** *(Required)* | **Read-only** | Required by GitHub for repository metadata and collaborator lookups. |
| **Repository permissions** | **Pull requests** | **Read and write** | Creates pull requests during `git brx review` and checks merge state during `git brx delete`. |
| **Repository permissions** | **Contents** *(Private repos)* | **Read-only** | Required on **private** repos during `git brx review` so GitHub can diff `head` and `base` refs (prevents `422: not all refs are readable`). |
| **User / Account permissions** | *(None)* | *None* | No account-level permissions are needed. |

![GitHub Fine-grained token repository permissions](../../../assets/github-token-permissions.png)

Confirm your token summary matches these permissions:

![GitHub Fine-grained token overview](../../../assets/github-token-overview.png)

#### Step 4: Export the Token
Generate the token (`github_pat_...`) and export it in your shell profile (`~/.bashrc`, `~/.zshrc`, or Git Bash):

```bash
export GITHUB_TOKEN="github_pat_xxxxxxxxxxxxxxxxxxxx"
# or
export GH_TOKEN="github_pat_xxxxxxxxxxxxxxxxxxxx"
```

## 3. Git transport (SSH vs. HTTPS) vs. API tokens

Using an SSH remote does not conflict with using a GitHub API token. `git-brx` separates Git transport from API calls:

| Layer | Transport / Client | Credential Used | Used By |
| :--- | :--- | :--- | :--- |
| **Git Transport** | Git over SSH (`git@github.com:...`) or HTTPS (`https://github.com/...`) | SSH key (`~/.ssh/id_*` / `ssh-agent`) or Git Credential Manager | `git fetch`, `git brx publish`, `git brx sync`, and `git brx update`. |
| **GitHub REST API** | HTTPS requests to `api.github.com` | Personal Access Token (`GITHUB_TOKEN` / `GH_TOKEN`) | Issue lookup (`git brx create`), PR creation (`git brx review`), and PR state checks (`git brx delete`). |

> [!NOTE]
> **Using SSH with `git-brx`:** Using SSH keys for Git push/fetch operations alongside a `GITHUB_TOKEN` for API requests is the standard setup.

## 4. Recommended repository settings

In your GitHub repository under **Settings** $\to$ **General** $\to$ **Pull Requests**, configure these two options:

### 1. Squash merge commit message
To make GitHub use the PR title generated by `git-brx` (`feat(#<issue>): <summary> (#<pr>)`) as the squash commit title:

1. Under **Pull Requests** $\to$ **Allow squash merging**, set the default commit message dropdown to **Pull request title** (or **Pull request title and commit details**).

![GitHub Allow squash merging dropdown set to Pull request title](../../../assets/github-squash-merge-setting.png)

If left on **Default message**, single-commit PRs use the individual commit message instead of the formatted PR title.

### 2. Automatically delete head branches
Enable **Automatically delete head branches** so GitHub deletes the remote topic branch (`issue/*`, `feature/*`, `epic/*`) on `origin` as soon as a PR is merged:

1. Under **Pull Requests**, check **Automatically delete head branches**.

With this enabled, running `git brx delete` after merging a PR sees that the remote branch is already gone, switches back to `main`, deletes the local branch, and prunes `origin`—without needing `--force` or manual cleanup on GitHub.

## 5. Branch prefixes & label mapping

During `git brx create <branch>`, `git-brx` checks the issue's GitHub labels to verify that the branch prefix matches the issue type.

### Default GitHub label mappings
New GitHub repositories ship with default labels like `bug` and `enhancement`. `git-brx` maps these by default:

* **`bug`:** Maps to `issue/` (blocks creating `feature/` or `epic/` branches for bugs).
* **`enhancement`:** Maps to `[issue, feature]` (allows either `issue/<id>` for small tasks or `feature/<id>` for larger work).
* **Unlabeled issues:** Default to `issue/<id>`.

> [!NOTE]
> GitHub does not create `feature` or `epic` labels by default. `git-brx` includes preset mappings for both, so if your team wants to use `feature/<id>` or `epic/<id>` via those labels, create them in your repository's GitHub label settings.

### Custom labels & multi-branch routing
If your repository uses custom labels (e.g., `kind/feature`, `type:bug`, `task`), map them under `branch.mapping` in `.git-brx.yaml`:

```yaml
branch:
  template: '^(issue|feature|epic)/[1-9][0-9]*$'
  mapping:
    # Direct raw GitHub labels (case-insensitive):
    "kind/bug": "issue"
    "enhancement": [issue, feature]   # Dual-mapping: allow either issue/ or feature/
    "feature": "feature"              # Custom label created in GitHub
    "epic": "epic"                    # Custom label created in GitHub
    "task": "issue, feature, epic"   # Comma-separated alternative syntax

    # Domain types:
    Bug: "issue"
    Story: "feature"
    Epic: "epic"
```

If you try to create `feature/10` for an issue labeled `bug`, `git-brx` rejects it:
```text
[git-brx] Error: Issue type 'bug' is not allowed on 'feature' branch
[git-brx] Hint: Use 'issue' branch or check mapping rules
```

## 6. Full GitHub configuration reference (`.git-brx.yaml`)

```yaml
platform: github

# Reviewer routing & merge rules
review:
  merge:
    instructions: true              # Injects merge strategy guidance and branch cleanup into PR
    strategy: squash                 # Global fallback strategy (squash | merge | rebase)
    strategies:
      sources:                       # Match against PR source branch (HEAD)
        "epic/*": merge
        "release/*": merge
      targets:                       # Match against PR target branch (BASE)
        "epic/*": merge
        "release/*": merge
  template: .github/pull_request_template.md
  mapping:
    paths:
      "internal/ui/**": [carol, dave]
      "internal/git/**": [bob]
      "docs/**": [tech-writer]
    labels:
      security: [charlie]
      backend: [alice, bob]
    branches:
      "epic/*": [lead-architect]
    default: [team-lead]            # Fallback reviewer
```
